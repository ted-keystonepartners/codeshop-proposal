01

지금 보이는 문제

1요청한 대로 만들어지지 않습니다

사례
  • 정산 화면 — 지난달 이익금을 이월해 자세히 보여 주는 부분
  • 일일업무보고 — 전달사항 내용이 분리되는 문제
드러난 때
주간 리뷰. 이미 다 만든 뒤였습니다.
원인 · 요구사항을 글로 정하지 않은 채 개발에 들어가고, 웹 화면인데도 와이어프레임으로 먼저 확인받는 단계가 빠져 있습니다.

2진척이 보이지 않습니다

사례
“문자 보내는 기능 개발하느라 다른 일정을 못 했다”가 반복됩니다.
오가는 말
“속도 내겠습니다”“이래서 못 했습니다”“다 됐습니다”“금방 하겠습니다”
원인 · 과제를 통째로 한 덩어리로 다뤄, 무엇이 끝났고 무엇이 남았는지 셀 단위가 없습니다. 그러니 말로 답할 수밖에 없습니다.
02

지금 흐름과 개선 흐름

같은 요청 하나가 어떻게 흘러가는지 나란히 놓았습니다. 왼쪽 줄은 대표님, 오른쪽 줄은 개발팀이 하는 일입니다.

지금 — 고리가 크고 늦게 돕니다어긋남이 개발을 다 끝낸 주간 리뷰에서 드러나, 되돌아가면 처음부터 다시 만들고 다른 과제까지 밀립니다.
개선 — 고리가 작고 일찍 돕니다어긋남은 개발 전 와이어프레임에서 걸러지고, 늦어지는 일은 WBS 항목 하나 단위로 미리 보입니다.
03

와이어프레임 — 만들기 전에 화면을 맞춥니다

와이어프레임은 색과 디자인을 빼고, 화면에 무엇이 어디에 놓이는지만 그린 설계 그림입니다. 웹 화면은 이것만 보면 결과를 거의 그대로 짐작할 수 있습니다.

개발 전요청과 다른 점이 드러나는 시점
04

WBS — 과제를 작업 단위로 나눠 관리합니다

WBS는 과제 하나를 실제로 손이 가는 작업까지 나눈 목록입니다. 작업마다 프론트·백엔드·서버·API 연동 중 무엇인지, 누가, 며칠, 지금 어떤 상태인지를 적습니다.

그러면 진척을 말이 아니라 표로 이야기하게 됩니다.

  1. 작업 하나는 1~3일 크기로 나눕니다. 그보다 크면 더 나눕니다. 그래야 늦어짐이 하루 단위로 보입니다.
  2. 상태는 완료 · 진행 중 · 대기 · 지연 네 가지로만 적습니다.
  3. 늦어질 것 같으면 주간 리뷰를 기다리지 않고 사유와 새 날짜를 그때 적습니다.
  4. 도구는 상관없습니다. 지라든 공유 표든, 대표님이 언제든 열어 볼 수 있으면 됩니다.
